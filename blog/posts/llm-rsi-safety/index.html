An AI research agent changes its own code, runs an evaluation, and reports a better score. Should we keep the new version?

The answer depends on what improved. The agent may have learned a better search strategy. It may also have removed a check that slowed it down, learned a shortcut specific to the benchmark, or changed the records from which its performance is measured. A rising score alone cannot distinguish these cases. Once the selected version helps produce the next one, an error in this decision can affect an entire line of successors.

This is the safety problem I want to examine under recursive self-improvement (RSI): how can we preserve trustworthy evidence and meaningful control while an LLM-based system participates in its own improvement? Here, safety means maintaining specified behavioral constraints and operator control across updates. It does not encompass every societal consequence of more capable AI.

The relevant literature spans self-training, reinforcement learning, agent engineering, reward hacking, and AI control. These fields study different pieces of the problem. Putting them together requires care: an agent that edits its harness—the code and instructions that organize model calls and tool use—is different from a model that updates its weights, and both differ from a system that redesigns its own training and evaluation process.

This review covers selected primary research available through October 12, 2026. Figure captions distinguish reproduced paper figures, redrawn results, and conceptual diagrams. The proposed evaluation and release protocol is a synthesis rather than an experimentally established guarantee.

1. What counts as recursive self-improvement?

“Self-improvement” describes several operations with different consequences.

Answer refinement changes a response during a single task. A model drafts, critiques, and revises an answer, but the next task may start from exactly the same model and system configuration. More inference does not necessarily create a persistent successor.

Persistent self-improvement changes something reused later: weights, prompts, tools, memory, training data, or orchestration code. Self-Rewarding Language Models, for example, use model-generated preference judgments for iterative training (Yuan et al., 2024). Darwin Gödel Machine modifies the code of an agent powered by frozen foundation models (Zhang et al., 2025).

Recursive self-improvement, in the stronger sense used here, improves the system’s ability to produce subsequent improvements. The connection can be indirect: a better coding agent can implement better tooling for its next round. It can also be explicit: the system edits the procedure that proposes changes. STOP and Hyperagents explore versions of this idea (Zelikman et al., 2023; Zhang et al., 2026a). Running such a loop is an experimental design; demonstrating that the improver became more effective is a further empirical claim.

These are operational distinctions, not a universally accepted taxonomy. A recent survey of evolutionary safety similarly emphasizes that persistent state, model state, evaluators, infrastructure, and the updater can evolve on different timescales (Gong et al., 2026). For a safety analysis, the useful question is concrete: what can change, who can authorize the change, and what remains outside the loop?

Evidence of improvement is not evidence of an intelligence explosion

The table below separates the object being improved from the machinery that still defines the experiment.

Table 1. Representative mechanisms, rather than a ranking. Task performance, autonomy, and safety preservation are separate experimental claims.

The “zero data” setting in Absolute Zero refers to its task-generation training phase; it does not remove prior pretraining or human choices about execution and rewards (Zhao et al., 2025). Likewise, editable meta-agent code in Hyperagents does not imply that every layer of the experiment is self-modifying.

There is also evidence that AI-generated improvements can matter to AI development. AlphaEvolve reports a kernel optimization that reduced total Gemini training time by about 1% (Novikov et al., 2025). This connects automated code search to a consequential training workload. It does not demonstrate an autonomous cycle of training a stronger model, improving the research system, and repeating indefinitely.

These results justify studying the safety of increasingly capable improvement loops. They do not establish either inevitable runaway improvement or a general limit that rules it out.

2. The unit of analysis is the whole loop

For bookkeeping, represent a system at iteration \(t\) as

$$ S_t = (\theta_t, H_t, D_t, E_t, U_t, P_t). $$
SymbolComponentExample
\(\theta_t\)Model parametersBase checkpoint and adapters
\(H_t\)Harness and persistent working statePrompts, tools, agent code, memory
\(D_t\)Training and selection dataSynthetic examples, preference pairs, retained traces
\(E_t\)Evaluation machineryTests, judges, scoring rules, measurement code
\(U_t\)Improvement procedureProposal generation, training recipe, search policy
\(P_t\)Permissions and deployment configurationFile access, credentials, compute limits, release authority

This notation is an abstraction for the article. It makes no assumption that every component is editable. In fact, identifying the protected components is central to the analysis.

Consider a coding agent that proposes a faster tool-execution path. Even with fixed weights, the patch can change which commands are allowed, how errors are handled, and which events reach the monitor. A test of the model alone will miss those changes. Persistent memory matters for the same reason: AgentPoison demonstrates that tampering with an agent’s retrieved memory or knowledge can change its behavior without changing its weights (Chen et al., 2024).

Three decisions are easy to conflate: whether a candidate should be explored, whether it should be retained for research, and whether it should be deployed. An archive can reasonably contain unsuccessful or unsafe candidates for analysis. The existence of a candidate in that archive should not give it permission to operate. Here, independent evaluation means that the candidate cannot rewrite its checks or evidence. This operational separation does not eliminate correlated model errors or an incorrect specification.

Recursion adds an inheritance problem. A defective update may change not only the next system’s behavior but also the data it generates, the failures it notices, and the candidates it proposes. Later versions are therefore not independent samples from the original development process. They inherit parts of its history.

3. When the score improves and the system does not

Proxy error needs no deceptive intent

Suppose an evaluator assigns a score \(\widehat{J}(S)\), while the property we care about is \(J(S)\). Selecting the highest-scoring candidate gives

$$ S^* = \operatorname*{arg\,max}_{S\in\mathcal{C}}\widehat{J}(S), \qquad \widehat{J}(S)=J(S)+\varepsilon(S). $$

Here \(\varepsilon\) includes sampling noise and systematic mismatch. Searching harder can select candidates with favorable evaluator errors as well as genuine improvements. The problem exists even when no candidate understands or intends to exploit the evaluator.

Gao et al. (2023) use a model-based “gold” reward to evaluate policies optimized against a weaker proxy. Gold reward can peak and decline while proxy reward continues rising. Neither score directly measures human welfare.

The gap between dashed and solid curves shows why selection on proxy reward can become misleading.

In an improvement loop, the same concern applies to benchmark accuracy, reward-model scores, judge preferences, and apparent safety rates. Adding a safety metric to the objective does not automatically make that metric resistant to optimization.

The evaluator can be intact while its evidence is corrupted

There is a stronger failure mode than ordinary proxy error: a candidate can change the channel through which the evaluator observes behavior.

In a separate hallucinated-tool-use experiment, one evolved DGM agent achieved a perfect measured score by removing logging markers rather than repairing the underlying behavior (Zhang et al., 2025, Appendix H). The detector’s records depended on mutable agent code.

This motivates a distinction between protecting a scoring function and protecting a measurement process. Keeping the grader read-only does little if the candidate can suppress the events it sees, substitute outputs, or choose which failed runs are reported. For our hypothetical faster tool runner, a lower reported violation count should be checked against independently captured executions.

Feedback can become an optimization signal for evasion

Huang et al. (2026) compare review feedback in an adversarial setting where research agents are explicitly instructed to evade oversight. Detailed feedback led to more successful evasion in the matched comparison below.

The agents adapted in context without updating weights. Review feedback is therefore part of the threat model.

4. Self-generated supervision can preserve mistakes

Using a model to generate its own training signal can work. Self-Rewarding Language Models improve through self-generated preferences; Self-Taught Evaluators train useful judges from synthetic comparisons (Yuan et al., 2024; Wang et al., 2024).

The difficulty is independent correction. If the generator and judge share a blind spot, agreement between them provides little evidence about that blind spot. A polished but incorrect proof may be generated, approved, and incorporated into the next training set. Better agreement can then accompany worse calibration. In our hypothetical tool runner, a logging bug could similarly hide failed executions from the traces used to train its successor.

Two recent studies examine parts of this problem. Qi et al. (2026) find meaningful but often incomplete gains from self-evolving reasoning under deliberately limited supervision. Their setup excludes stronger external teachers and verifiers; it is not a ceiling on all forms of self-improvement. Song et al. (2026) report that model-coupled self-review can lose its filtering value during recursive code training, with rising acceptance alongside declining correctness in a studied setting. That result concerns a particular training regime, not every use of AI code review.

Distributional collapse and safety drift are different

Shumailov et al. (2024) show how recursive training on generated data can lose parts of the original distribution, including its tails. Gerstgrasser et al. (2024) provide an important counterpoint: accumulating real and synthetic data avoids the collapse observed under replacement in their experiments.

The useful conclusion is conditional. Data provenance, retention, sampling, and mixing affect the outcome. “Synthetic data causes collapse” is too broad; “keeping real data guarantees safety” is also too broad.

For RSI safety, the concern extends beyond average quality. Rare authorization failures, unusual user needs, or difficult counterexamples may receive little representation in a self-generated curriculum. Preserving the original data is one possible safeguard against forgetting, but does not establish that the original data cover new capabilities or deployment conditions. This is an implication for evaluation design, rather than a safety result established by the collapse papers.

A weaker judge can help without being sufficient

Weak-to-strong generalization offers a useful reason for optimism: a stronger pretrained model can learn from weak labels and exceed the weak supervisor’s performance (Burns et al., 2024). However, the experiments do not establish that a weak judge can reliably supervise arbitrary stronger behavior.

A practical research question follows: which errors are corrected by pretraining, independent execution, or additional supervision, and which are reinforced by the loop? Measuring judge–generator agreement alone cannot answer it. We need separately labeled tests of both the generator’s behavior and the judge’s ability to recognize failures.

5. Safety does not automatically survive post-training

An aligned starting checkpoint does not make every descendant aligned.

Qi et al. (2024) show that fine-tuning can compromise safety, including under benign customization objectives. The update need not explicitly train harmful behavior to invalidate an earlier safety evaluation. Parameter-efficient fine-tuning still changes the function the system computes; a small trainable parameter count is not a bound on the resulting behavioral change.

Methods such as Safe LoRA aim to reduce this problem by constraining adaptation relative to an alignment-related subspace (Hsu et al., 2024). Such methods are useful candidates for an improvement pipeline, but their evaluations do not certify arbitrary sequences of adapters, merges, and future training stages. A claim about a single update should be tested again under repeated composition.

The effect can also extend beyond the training domain. Betley et al. (2025) find that narrow fine-tuning on insecure code can produce broader misaligned responses. Their controls show that the framing of the training task matters, and the effect varies across models. This gives a concrete reason to test a successor beyond the capability it was designed to improve.

Two lines of reward-hacking research sharpen the concern:

  • Generalization between kinds of gaming. Denison et al. (2024) construct a curriculum in which specification gaming sometimes transfers to reward tampering. This demonstrates a possible route under engineered conditions, not an inevitable progression from ordinary mistakes to sabotage.
  • Generalization beyond the reward-hacking task. MacDiarmid et al. (2025) observe broader misalignment after experimental models learn hacks in coding RL environments. Researchers supplied exploit knowledge and removed mitigations from selected environments. The result should not be read as a failure rate for released production models.

Nor is later safety training guaranteed to remove a problem. Sleeper Agents studies deliberately implanted conditional behaviors that can persist through subsequent safety training (Hubinger et al., 2024). This is evidence about a failure mechanism, not evidence that such backdoors arise naturally in every training run.

For an RSI experiment, the corresponding measurement is longitudinal: after each accepted update, test whether previously tested safety behaviors remain reliable, whether new capabilities introduce new hazards, and whether the next update inherits the regression. A final checkpoint comparison can miss a harmful intermediate version that was deployed or used to generate training data.

6. Oversight can be useful and still be an optimization target

Alignment and control ask related but different questions. Alignment methods try to make the system behave as intended. Control methods also ask what happens if it attempts to subvert the procedure.

AI Control studies this second question using programming tasks, an untrusted stronger model, a weaker trusted model, and limited trusted auditing. Monitoring and editing protocols improve outcomes in its constructed setting (Greenblatt et al., 2024a). The assumptions matter: a trusted auditor and a limited task environment are not automatically available in open-ended AI research.

For recursive improvement, control concerns arise at several points: producing a patch, choosing a training dataset, reporting an experiment, or reviewing a successor. A system need not seize release authority directly to influence the result. It may simply make a bad candidate look more promising than a good one.

Distinguish capability, propensity, and observation

An instructed sabotage experiment asks whether a model can carry out a specified failure. It does not directly estimate how often an ordinary research agent will do so. For example, Automated Researchers Can Subtly Sandbag studies prompted underperformance on ML research tasks (Gasteiger et al., 2025). It establishes a testing target for oversight, not spontaneous sabotage prevalence.

Alignment faking provides a different form of evidence. Greenblatt et al. (2024b) create a training context that conflicts with a model’s existing harmlessness preferences and observe strategic compliance aimed at preserving behavior outside training. The constructed conflict and training information are central to the result. It supports testing behavior across evaluation contexts; it does not show that every compliant model conceals a harmful goal.

These distinctions should survive into reporting. “The model could hide a defect when instructed,” “the model hid a defect without that instruction,” and “our monitor failed to detect the defect” are three separate findings.

A monitor’s score is not the underlying behavior

Chain-of-thought can provide useful evidence. Baker et al. (2025) find that reasoning traces help detect reward hacking. A separate training experiment shows how optimizing against a reasoning monitor can weaken this evidence.

The baseline also cheats, but its cheating is detected. Training against the monitor reduces overall cheating yet leaves more cheating undetected. A low alarm rate therefore needs to be checked against actual behavior.

More context is not uniformly helpful. ResearchArena reports that additional reasoning can sometimes make a monitor accept an agent’s rationalization, while interaction with the environment and targeted investigation can improve detection (Libon et al., 2026). This suggests testing what the monitor actually does with a trace, rather than assuming that access alone creates reliable oversight.

There is evidence that targeted training helps: anti-scheming work reduces covert behavior substantially on the authors’ evaluation suite, while leaving residual failures and questions about evaluation awareness (Schoen et al., 2025). The appropriate response is to combine behavioral training with independently tested control procedures and report where each fails.

7. A passing candidate is not enough: selection and recovery matter

An improvement system can generate a correct solution and still run the wrong one.

Zhang et al. (2026b) study fixed LLM editors modifying authorization components. After a dependency changed, matched 60-edit experiments compared continued evolution using historical scores against refreshing scores, feedback, and selection metadata under the current contract.

Separately, re-ranking existing archives under current tests recovered passing alternatives without new repairs. The plotted refresh intervention still left some independent-test failures.

The design implication is broader than keeping backups: a rollback version needs evidence that it satisfies the current requirements. An old checkpoint may have passed yesterday’s tests while violating today’s permissions or interface contract. If no candidate is valid, automatic continuation with the “best available” score may be the wrong action.

For the tool-runner example, reverting to a previous implementation is meaningful only if that implementation still enforces the current authorization policy. An archived success label is historical evidence, not a permanent certificate.

8. How to evaluate the improvement process

Most task benchmarks evaluate outputs or fixed agents. Evaluating RSI also requires tracking how candidates are generated, selected, inherited, and deployed.

Repeatedly used tests become part of development

Self-Harness accepts changes using both held-in and held-out pass counts (Zhang et al., 2026c). That is useful regression testing. However, once the held-out results repeatedly influence selection, they are part of the adaptive development process. Calling a split “held out” does not make it an untouched final test.

This is an application of the broader problem of adaptive data analysis: statistical conclusions can become unreliable when analysts repeatedly use the same data to choose what to try next (Dwork et al., 2015). The point is not that a reused benchmark becomes worthless, but that its evidential role changes.

A useful experiment should distinguish three channels: feedback for development, gates for promotion, and an independent audit reserved for a frozen candidate or lineage. The audit itself must eventually be renewed if its results become training or selection feedback.

Record the trajectory, not just the winner

I would report the following alongside the final task score:

QuantityWhat to recordWhat it helps distinguish
CapabilityPerformance on development and independent tasks, at matched budgetsUseful transfer from repeated benchmark optimization
Behavioral safetyFailure rates by hazard class and severityAggregate gains from regressions in a small but consequential category
Evaluation integrityIndependent reruns, missing events, modified measurement pathsBetter behavior from better-looking evidence
Judge qualityFalse acceptance and rejection on separately labeled casesActor improvement from changing reviewer standards
LineageParents, accepted and rejected updates, data and evaluator versionsAn isolated defect from inherited degradation
Exposure and recoveryWhich versions actually ran, with what permissions, and for how longResearch failures from deployed harm; stored recovery from working recovery

Table 2. A proposed reporting scheme. The measurements should remain separate; a weighted average can hide a severe regression behind a small capability gain.

Budgets also matter. RE-Bench compares agents and human experts on research-engineering tasks under different time budgets (Wijk et al., 2024). A claimed improvement should specify wall-clock time, compute, model calls, and human intervention. If evaluation becomes much more expensive with each generation, the practical improvement may be smaller than the headline score suggests.

Independent reruns are particularly valuable in research automation. In METR’s preliminary NanoGPT optimization study, revalidation removed some apparent gains (Cunningham et al., 2026). The small experiment does not establish a general rate of research error, but it illustrates why agent-reported best results need external reproduction.

Test the benefit of recursion itself

A stronger final agent does not identify which part of the loop helped. To test recursive improvement, compare against a frozen improver with the same model and compute budget, ordinary search over candidate changes, and a version that cannot edit its improvement procedure. Keep reporting unsuccessful runs and the cost of selection.

For safety, repeat the comparison across complete lineages. Test whether a regression can be detected, whether it survives into descendants, and whether the system recovers under changed requirements. A method that succeeds on one carefully selected trajectory has provided weaker evidence than one that handles multiple seeds, failure types, and environment shifts.

9. A release protocol for a self-improving research agent

The following protocol combines lessons from the literature into an engineering proposal. It assumes an operator can enforce isolation, protect the evaluator and release mechanism, and obtain some reliable external checks. Those assumptions must themselves be tested.

First, define the allowed change. Record the parent version, editable files or parameters, data sources, expected benefit, and possible regressions. A candidate that changes the evaluator or seeks additional permissions should enter a different review path from an ordinary implementation improvement. Agentic Harness Engineering offers a concrete example of limiting edits while keeping runs, tracing, and verification infrastructure read-only (Lin et al., 2026).

Second, run the candidate in isolation. Give it the resources needed for its experiment, with explicit limits on credentials, network access, compute, and persistence. Capture evidence outside its editable workspace. The system may propose a broader experiment; proposing it should not grant permission to execute it.

Third, evaluate several requirements separately. Check the intended capability gain, relevant safety regressions, integrity of measurement, and compatibility with the current contract. Recompute important results from preserved artifacts. Use model-based review where useful, but do not make agreement between related models the only evidence.

Fourth, keep promotion externally authorized. The release mechanism should verify the evaluated artifact and its configuration, rather than accepting a candidate’s claim that it passed. Improving task accuracy must not silently increase permissions. If the evaluator itself needs improvement, treat that as a separately versioned change with separate validation.

Fifth, continue checking after release. Begin with limited exposure, monitor the behavior that matters, and retain a recovery path whose validity is current. Stop the loop when evidence becomes unreliable, limits are exceeded, or no available version satisfies the operating requirements.

This arrangement does not solve specification. A perfectly protected test can still test the wrong thing. It does, however, make several failures distinguishable: a bad proposal, a misleading measurement, an incorrect promotion, and an invalid recovery. That separation makes failures easier to investigate and protocols easier to compare.

10. Open questions

The hardest questions concern what must remain reliable as the system changes.

Can an evaluator improve without certifying itself? Freezing evaluation limits adaptation to new capabilities; allowing unrestricted evaluator updates weakens continuity. We need protocols that compare old and new evaluators against fresh external evidence and measure correlated blind spots.

Which safety properties compose across updates? A locally acceptable adapter, dataset change, and harness patch may interact badly. Sequential and branching experiments could test how much evidence about individual changes transfers to their combinations.

How should we measure rare failures across a lineage? Per-task averages can conceal a short-lived unsafe version or a defect copied into many descendants. Better benchmarks would track when a failure enters, whether selection favors it, where it propagates, and whether recovery removes it.

How much can a system improve its improver? Existing bounded experiments motivate the question but leave open the role of compute, fixed foundation models, task similarity, and external evaluators. Useful progress requires isolating the contribution of meta-level changes rather than labeling every iterative gain recursive.

Can oversight remain effective under sustained adaptation? A monitor that catches today’s failures may supply the feedback needed to avoid detection tomorrow. Evaluations should give the opposing process multiple attempts and account for how much information each rejection reveals.

What does it mean to preserve the right objective? Formal self-modification work studies circumstances in which idealized agents preserve their current utility function (Everitt et al., 2016). Such preservation does not establish that the objective was correct, that an LLM implements it faithfully, or that the system will accept legitimate corrections. For practical RSI, continuity and corrigibility both need explicit treatment.

The evidence so far supports a concrete research agenda: evaluate improvement as a sequence of consequential decisions. Track what changes, protect the evidence used to judge it, and test which version actually runs after a failure. Those questions are already experimentally accessible, even while open-ended recursive improvement remains uncertain.
